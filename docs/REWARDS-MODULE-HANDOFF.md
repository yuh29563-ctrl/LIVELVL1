## 当前已知的“奖励”含义

LIVELVL 中存在两类容易混淆的奖励概念：

1. **收集奖励卡**：已经实现。伙伴成熟或隐藏条件达成后产生 `PendingCardReward`，用户点击“收下”，卡片飞向“收集”Tab，并持久化为 `OwnedCollectible`。
2. **现实奖励商城**：尚未实现。本交接所说的“奖励模块”指这一部分，即用户使用金币兑换自己设定的现实奖励。

两者必须保持领域隔离。现实奖励商城不能复用、改写或破坏收集奖励队列。

仓库目前唯一明确的产品文案位于：

- `LIVELVL/LIVELVL/Rewards/RewardPlaceholderView.swift`

文案为：“下一阶段可以用金币兑换你为自己设定的现实奖励”。

既有 Collection 规格还明确提到 Debug 全量重置最终需要清除：

- 金币
- 奖励商品
- 兑换历史
- 本地商品图片目录 `RewardProductImages`

但当前 SwiftData schema 尚无金币、奖励商品和兑换记录模型，奖励 Tab 仍是占位页。

## 目前尚未定义，禁止擅自假设

以下产品规则在现有文档和代码中没有答案：

- 金币如何获得：按 XP、任务次数、难度、连续天数，还是独立规则。
- 历史金币是否因撤销任务而扣回，余额是否允许为负。
- XP 与金币的换算比例及每日上限。
- 奖励商品字段：名称、价格、备注、图片、分类、库存、重复兑换等。
- 商品由用户创建还是 App 预置，是否允许编辑、删除和归档。
- 兑换是立即完成，还是进入“待兑现—已兑现—取消”流程。
- 取消兑换是否退币，删除商品后历史记录如何展示。
- 图片是否只支持静态图，是否支持动图，图片尺寸与存储上限。
- 是否需要金币流水、筛选、排序、确认弹窗和兑换庆祝动画。

## 推荐的第一版 MVP（仅作为提案）

为了让下一轮讨论可以快速收敛，推荐提出以下最小闭环：

1. 奖励页顶部显示当前金币余额。
2. 用户可以创建现实奖励：名称、金币价格、可选备注、可选静态图片。
3. 奖励以卡片列表展示，支持编辑和归档，不直接硬删除有兑换历史的商品。
4. 点击兑换先二次确认；余额不足时不允许兑换。
5. 成功兑换原子地扣减金币并写入不可变兑换快照。
6. 历史页显示兑换时间、商品名称、当时价格和兑现状态。
7. 第一版不做账户、网络、云同步、社交、真实支付、商城后台、库存物流或远端图片。

仍需用户首先决定两项核心规则：

- 金币的获得方式。
- 兑换后是否需要“待兑现/已兑现”状态。

这两项会决定数据模型和撤销语义，不能在实现中途再猜。

## 推荐架构边界

在规格确认后，优先采用“本地 SwiftData 账本 + 本地图片文件存储 + 纯领域服务”结构：

- `CoinBalance` 或等价的单例账户模型：只保存可验证的余额或聚合状态。
- `CoinTransaction`：不可变金币流水，记录收入、兑换、退款及稳定业务键。
- `RewardProduct`：用户定义的现实奖励及当前展示状态。
- `RewardRedemption`：保存兑换时的商品快照，避免后续编辑商品篡改历史。
- `RewardProductImageStore`：图片存放到 Application Support 的 `RewardProductImages`，SwiftData 只保存稳定引用。
- `RewardStoreService`：处理创建、编辑、归档、兑换、退款等原子操作。
- `CoinAwardService`：只负责经用户确认的金币发放规则，不与 `CardRewardService` 混合。

关键不变量：

- 余额不能为负。
- 同一收入事件不能重复发币。
- 一次兑换要么同时扣币并写入记录，要么全部失败并回滚。
- 商品被编辑或归档后，兑换历史仍保留当时名称、价格和图片引用策略。
- 删除图片不能误删陪伴卡媒体或其他业务图片。
- Debug 全量重置必须覆盖新增模型和 `RewardProductImages`，失败时沿用现有部分失败报告语义。

## 必须采用的开发流程

1. **确认基线**
   - 检查用户希望从本地 `main` 还是包含 `a6b1b4c` 的 UI polish 基线继续。
   - 经用户确认后创建 `codex/rewards-mvp`。
   - 使用 `.worktrees/rewards-mvp` 隔离工作区。
   - 完整运行当前 Debug 测试并记录数量。

2. **先设计再实现**
   - 使用 `superpowers:brainstorming`。
   - 明确金币获取、撤销语义、兑换生命周期、图片范围和 MVP 验收标准。
   - 写入新的奖励模块设计规格并让用户审核。
   - 使用 `superpowers:writing-plans` 生成逐步实施计划。

3. **严格 TDD**
   - 每项行为先写失败测试并确认失败原因正确。
   - 写最小实现使其通过。
   - 每个领域任务完成后运行聚焦测试及完整回归。
   - 使用小而清晰的提交，不把模型、领域规则和大面积 UI 混成不可审查提交。

4. **持续查错循环**
   - 编译并运行聚焦测试。
   - 运行完整 Debug 测试。
   - 安装到 iPhone 17 Pro 模拟器。
   - 使用真实 UI 创建商品、余额不足兑换、成功兑换、编辑/归档、重启恢复、Debug 重置。
   - 检查 SwiftData 原子性、重复事件幂等、图片文件残留、动态字体、VoiceOver 和 Reduce Motion。
   - 发现问题后先用 `superpowers:systematic-debugging` 定位根因，再新增回归测试、修复并重复上述验证。

5. **终止条件**
   - 所有书面验收标准均有自动测试或明确的模拟器人工验收证据。
   - 聚焦测试和完整 Debug 测试为零失败。
   - App 重启后余额、商品和兑换历史一致。
   - 不存在重复发币、负余额、兑换记录丢失或孤儿图片。
   - 收集奖励飞行动画在真实模拟器坐标下重新验收通过。
   - 工作区无意外文件，且没有 `xcuserstate` 或无意义 `project.pbxproj` 改动。

不要承诺“完美”或无限循环。若同一阻塞条件连续出现三轮且无法继续，停止修改，保存诊断证据并向用户报告；不要通过删除测试、放宽断言或擅改产品规则来制造绿色结果。
